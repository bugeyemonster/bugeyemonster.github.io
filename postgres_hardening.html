PostgreSQL Security Hardening: A Comprehensive Assessment Guide

By Your Security Analyst Assistant

In today's interconnected world, database security is paramount. PostgreSQL, a powerful open-source object-relational database system, is no exception. While robust, a default PostgreSQL installation often lacks the necessary hardening to withstand sophisticated attacks. This guide provides a structured approach to assessing your PostgreSQL installation for security vulnerabilities, focusing on critical configurations and remote access.

Important Note: This assessment specifically considers PostgreSQL 14 running with an exposed port, including a scenario with a synchronously replicating secondary system. A compromise on one system can directly impact the other.

Understanding the Risks: Default Configuration Vulnerabilities

Many security vulnerabilities stem from unaddressed default settings. Here are seven common high-risk findings if no hardening has been applied:

# Finding Description Manual Verification in Configuration Files
1. Unencrypted Communication: Data transmitted over the network is unencrypted, as SSL/TLS is not enabled by default, leaving sensitive information vulnerable to network eavesdropping. Check postgresql.conf: Verify the line is set to ssl = on. If it is commented out (#) or set to off, encryption is not active.
2. Broad Remote Access: The server may be configured to listen on all interfaces (listen_addresses = '*') and potentially allows connections from any external network in pg_hba.conf, significantly increasing the attack surface. Check postgresql.conf: Verify listen_addresses is restricted to specific IP addresses (e.g., 192.168.1.10) or localhost, not *. Check pg_hba.conf: Look for any remote host entries using the unrestricted CIDR range 0.0.0.0/0.
3. Weak Authentication Method: Authentication for remote access may be set to less secure methods like trust or md5 instead of the more robust scram-sha-256, making it susceptible to credential theft or brute-forcing. Check pg_hba.conf: In remote host entries (for client or replication access), confirm the final column (the authentication method) is set to scram-sha-256 and not md5, password, or trust.
4. Default Superuser: The default postgres superuser role is active and may be accessible remotely, posing a high-privilege target for attackers to compromise. Check pg_hba.conf: Search for any remote host entries specifically allowing connections for the user postgres and ensure the access is either blocked or restricted to only localhost (127.0.0.1/32).
5. Unrestricted Replication User: The replication user account may be poorly secured or use overly permissive network access, potentially allowing an attacker to leverage the replication mechanism for unauthorized access or data exfiltration. Check pg_hba.conf: Review the dedicated host replication entry to ensure the IP range is limited strictly to the secondary replica's host address (/32) and uses a strong authentication method like scram-sha-256.
6. No Connection Rate Limiting: There is **no external mechanism** or database setting to aggressively log and block repeated failed login attempts, making the service highly vulnerable to brute-force attacks. Check postgresql.conf: While external tools are best, verify that logging is enabled with log_connections = on and log_disconnections = on to at least record the attack attempts for later analysis or for tools like Fail2ban.
7. Unnecessary Privileges: Database users may hold **unnecessarily broad default privileges** on new objects and databases, violating the principle of least privilege. Check with psql: Execute \du to check for non-administrative user roles that have the CREATEROLE or CREATEDB attributes. Run SHOW default_acl_config; to check default object privileges.

Comprehensive Security Checklist

This detailed checklist provides actionable steps and tools for a thorough security assessment of your PostgreSQL 14 server.

A. Network Access and Firewall Configuration

Item Check Detail Tools
**Firewall Status** Verify an **external firewall** (e.g., iptables, ufw, security group) is active on the host OS and configured to block all ports by default. sudo ufw status, sudo iptables -L -v -n, Cloud Console
**Port Exposure (Remote)** Confirm the PostgreSQL port (default **5432**) is only open to **trusted source IP addresses/networks** for clients. **nmap** (from an external host), **netstat / ss** (on the DB server), Cloud Console
**Port Exposure (Replication)** Confirm the PostgreSQL port is open **only to the secondary replica's specific IP** for replication traffic. **nmap** (from the replica host), **netstat / ss** (on the DB server), Cloud Console
**listen_addresses** Check postgresql.conf to ensure listen_addresses is restricted to required IP addresses, not set to *. grep postgresql.conf, psql (using SHOW listen_addresses;)
**Brute-Force Defense** Verify a tool like **Fail2ban** is installed, active, and configured to monitor PostgreSQL logs for failed logins and automatically block the attacker's source IP address. sudo systemctl status fail2ban, fail2ban-client status postgresql (on the DB server)

B. Authentication and Access Control (pg_hba.conf)

Item Check Detail Tools
**Allowed Hosts** Verify all pg_hba.conf remote entries use **specific, minimal CIDR ranges** (e.g., /32 for a single host) instead of wide ranges like 0.0.0.0/0. cat /path/to/pg_hba.conf
**Authentication Method** Ensure authentication for remote client and replication connections is set to the highly secure **scram-sha-256**. cat /path/to/pg_hba.conf
**Replication Entry** Verify the replication line in pg_hba.conf is **strictly limited** to the specific replication user and the secondary replica's IP. cat /path/to/pg_hba.conf
**Superuser Access** Confirm remote access for the postgres superuser is **explicitly disabled** or severely restricted to localhost access only. cat /path/to/pg_hba.conf
**Template Database Access** Ensure non-administrative users are denied access to the template0 and template1 databases. **psql** (attempting connection as a low-privilege user)

C. Encryption (SSL/TLS)

Item Check Detail Tools
**SSL Enforcement** Verify postgresql.conf has **ssl = on** and secure ciphers are configured via ssl_ciphers (to prevent use of weak encryption). psql (using SHOW ssl; and SHOW ssl_ciphers;)
**SSL Mode in pg_hba.conf** Check pg_hba.conf to ensure remote connections *require* SSL using the **hostssl** record type instead of host. grep hostssl /path/to/pg_hba.conf
**Certificate Validity** Confirm the SSL certificate and key files are present, correctly referenced in postgresql.conf, and are **valid (not expired)**. **openssl** (`openssl x509 -text -noout -in server.crt`)
**Client Connection Test** Attempt to connect using a client with **sslmode=disable** to ensure the server rejects the unencrypted connection. **psql** (e.g., psql "host=... sslmode=disable")

D. User, Role, and Replication Management

Item Check Detail Tools
**Strong Passwords** Confirm a strong password policy is enforced for all users, including the critical **replication user**. Manual review/audit, psql (checking password complexity policies if external tools are used)
**Role Permissions** Review all existing roles (\du) to ensure non-administrative users do not have **SUPERUSER**, **CREATEROLE**, or **CREATEDB** privileges. **psql** (using \du)
**Replication User** Verify the dedicated replication user only has the **REPLICATION** attribute and the **LOGIN** attribute, with no other administrative rights. **psql** (using \du replication_user;)
**Replication Slot Access** If using replication slots, ensure the replication user is the *only* one allowed to manage or drop these slots. **psql** (querying pg_stat_replication and checking user privileges)
**Search Path Hardening** Check the default search_path for users to ensure it does **not include 'public'** before other schemas, preventing possible public schema attacks. **psql** (using SHOW search_path;)

E. Vulnerability Scanning and Penetration Testing Tools

These tools are executed from an external client or attacker-simulated host to probe the exposed port and identify potential weaknesses.

Tool Purpose Example Commands
**psql Client** The primary tool for testing authentication, SSL enforcement, and configuration from a client perspective. psql -h <IP> -p 5432 -U postgres -W (Test authentication)
**nmap (with Scripts)** Used for port scanning, service version detection, and executing PostgreSQL-specific vulnerability checks. nmap -p 5432 --script pgsql-brute,pgsql-enum <IP>
**Hydra / `medusa`** Used to perform **brute-force password guessing** against the exposed service to test the effectiveness of password strength and rate-limiting. hydra -L users.txt -P passwords.txt <IP> postgres
**netcat (`nc`)** Basic tool to confirm TCP connectivity and sometimes grab simple banner information. nc -vz <IP> 5432

Conclusion

A proactive and thorough security assessment is crucial for maintaining the integrity and confidentiality of your PostgreSQL data. By systematically reviewing each item in this guide and implementing the recommended hardening measures, you can significantly reduce your database's attack surface and bolster its defenses against potential threats. Regular re-assessment and staying updated with PostgreSQL's security advisories are also vital for long-term security.
